# Milestone 8 notes: shared instances

Planned with the owner (this repository's maintainer) on 2026-11-02; nothing here is built yet. Each slice adds what it builds to this file as
it lands. The plan card: an instance many people share. Accounts work the way n8n's do, a person sees only the
companies they are given, companies cannot reach each other through the workers, and the install is
`docker compose up` on one machine or the chart on a cluster. Done when someone who is not the author installs
it with Docker from the docs and runs a goal; M6 set the same bar for the cluster, and it was never met.

M8 comes after M7 and after Company model providers slices 5 to 7, so that every company on an instance thinks
with its own key.

## Where it starts

Checked on `main` at `0b1a462`, 2026-11-02:

- Sign-in is OpenID Connect (`apps/board/src/auth/oidc.ts`) or dev login; the board keeps no passwords. Who may
  found a company is an env var (`ROSTERDOCK_COMPANY_CREATORS`); unset, only the first company on an empty
  board.
- Roles are per company (owner, admin, reviewer, viewer, teammate), and nothing sits above a company. A viewer
  sees the whole company.
- `docs/security.md` says to put only companies that trust each other on one board: every worker holds
  `DATABASE_URL`, a teammate token lasts up to 30 days and nothing revokes it, and a stdio server runs inside the
  board pod as the board.
- Compose is for development: dev login and dev passwords written in, ports on 127.0.0.1, no git token, and the
  worker behind a profile. The published worker image leaves Claude Code out, as its licence requires.

## Decided

### Accounts

- A fresh install opens on a sign-up screen, and whoever fills it in becomes the instance's Owner. The operator
  can set the Owner from env vars instead. On Kubernetes the chart requires an Owner from a Secret or OpenID
  Connect, so a fresh install behind a public address never shows a screen a stranger could claim. The Docker
  install listens on 127.0.0.1, so its screen is reachable only from that machine.
- Instance roles as n8n has them: Owner (one per instance), Admin and Member. Owners and Admins open and manage
  every company, create companies, and invite and remove people. A Member sees only the companies they are in,
  and cannot create one.
- Inside a company a person holds one of today's roles, and can hold different ones in different companies.
- Invites go by email when SMTP is set, and otherwise as a link the Owner or Admin copies; a link works once
  and expires.
- Passwords are stored as argon2id hashes. A reset is an email with SMTP, otherwise a link an Owner or Admin
  copies, and a command in the board's container resets a locked-out Owner. A hash is a verifier, not a secret
  value, so the secrets rule holds; `docs/security.md` covers the new surface (hashing, rate limits, resets).
- Authenticator codes for anyone, with recovery codes, and the Owner can require them for every password
  sign-in. Where a code's seed is kept is open (below).
- OpenID Connect stays, for the chart and for single sign-on. With built-in accounts,
  `ROSTERDOCK_COMPANY_CREATORS` goes.

### Isolation

The three fixes the backlog designed, before several owners share an instance, and the endpoint seal that
belongs with the first:

- The worker gets a database role of its own that reaches only the queue's schema (`pgboss`). Repository tests
  run as another user, so `/proc` does not show them the worker's environment; every run gets a fresh HOME and
  TMPDIR; and the engine's process group is killed when it ends, as the test step's is.
- The endpoint seal: an HMAC, with a key only the board holds, over a provider's or a connection's company,
  kind, endpoint, region and credential names, checked at every use, so a write to the database cannot repoint
  where a key is sent.
- Teammate tokens are listed and revoked in Settings, as events.
- A stdio server runs as another user or in a sidecar, without the board's environment, a file secret store or
  the service account token.

### Installs

- Docker: one `docker compose up` brings up the board, web, worker, Postgres and MinIO, with real accounts and
  no dev login. Secrets are made on first start into a volume, never into Postgres. The worker image is built on
  the machine with Claude Code installed there; Codex is in the image already. Migrations run on start. HTTPS
  (a reverse proxy, or Tailscale Serve through `deploy/scripts/serve.sh` and `docker-compose.public.yml`) and
  backups are the operator's, and `docs/install.md` says how.
- Kubernetes stays the production route: high availability, an external Postgres, OpenID Connect. The chart
  gains the worker's database role and the stdio sidecar.

## Slices

Each slice is green on typecheck, lint, format and the offline tests (and helm lint when the chart changes),
carries its doc lines, and is committed before the next starts. The slices become GitHub issues and are built
the way M7's are (`docs/m7.md`, Slices).

- **0. This file and the plan card**, with M7's. Done when the owner approves them.
- **1. Accounts.** Passwords (argon2id), the first-run screen, the Owner from env or a Secret, sessions and
  sign-in rate limits; Owner, Admin and Member in the guard. Done when the guard tests cover every instance
  role on every instance route, and the first-run screen refuses once an Owner exists.
- **2. Invites and resets.** By email with SMTP or by a copied link, single use and expiring, and the reset
  command. Done when a link works once and then expires, and a reset ends the account's other sessions.
- **3. Authenticator codes.** Codes, recovery codes, and the Owner's requirement. Done when RFC 6238's published
  test vectors pass, and a required code stops a sign-in without one.
- **4. Access.** Owners and Admins create companies and add people with company roles; a Member sees only their
  companies; the instance's rules and its say on autonomy. Done when a Member sees nothing of a company they are
  not in, in every list and route test.
- **5. The worker's own database role, and the seal.** With repository tests as another user, the fresh HOME
  and TMPDIR, and the process group. Done when, as the worker's role, a test cannot read a company's table, a
  run cannot see the worker's environment, and a repointed endpoint is refused.
- **6. Tokens.** List and revoke, as events. Done when a revoked token is refused at once.
- **7. Stdio servers.** Run as another user or in a sidecar, no longer as the board. Done when a stdio server
  cannot read the board's environment or its secret store.
- **8. The Docker install.** Done when, on a clean machine, `docs/install.md` alone goes from
  `docker compose up` to a signed-in Owner and a first real run.
- **9. The chart.** OpenID Connect or an Owner from a Secret, the worker's role and the sidecar. Done when helm
  lint passes and the smoke install signs in with an Owner from a Secret.
- **10. The demo and the guides.** Done when the demo below runs from the docs.

## The rules it changes

- "Roles from day one" gains the instance's Owner, Admin and Member (slice 1), checked by the same guard as
  the company roles.
- "Everything is per company" gains a level above the companies: accounts, instance roles, invites and the
  instance's rules belong to no company. Where their rows and events live is open (below). An instance's
  Owners and Admins can open every company, and what they change there is in its activity, as anyone's is.

## Open

- Where an authenticator code's seed is kept. A seed is a secret value, so it cannot sit in Postgres
  (`CLAUDE.md`); the board's secret store is the likely home. Slice 3 waits for the answer.
- Where the instance's own rows and events live. "Every row carries `company_id`" and "One event stream" are
  written for companies; accounts, instance roles, invites and the instance's rules have no company. Slice 1
  waits for the answer.

## Demo script

1. On a fresh machine, `docker compose up`; the first-run screen makes the Owner.
2. Invite a Member by a copied link; they set a password and turn on authenticator codes.
3. Two companies with different owners, each with only Peter, each on its own Anthropic key.
4. An autonomous goal in each; Peter staffs each one.
5. The Member of one company sees nothing of the other.
6. A revoked teammate token stops working at once.
7. The chart on a cluster with OpenID Connect, and the same again.

## Not in M8

- Company model providers slices 8 to 11 (Bedrock, OpenAI, Azure OpenAI and compatible servers through the
  gateway, Peter on every kind, AWS access keys): after M8.
- SAML, LDAP and custom instance roles.
- Binding a run token to the pod that claimed its run: the backlog.
