# Milestone 6 notes: deployable

What landed, how an install goes, what the done criterion means in the tree, and what is deliberately
left for later. The plan card: a production Helm chart (external Postgres and S3, OIDC, secrets, resource
limits, HPA, network policies for worker pods); company, department and teammate templates as importable
files; a costs export and a monthly cost report with chargeback tags per project; observability
(OpenTelemetry traces per run, Prometheus metrics, structured logs, pod CPU and memory in the live panel);
behavioural drift detection and sandbox network policies per department; an install guide, an operator
guide and security notes. Done when someone who is not the author installs into a clean cluster from the
docs and runs the M4 demo there.

## Sign-in

Production signs in through one OpenID Connect provider (`ROSTERDOCK_OIDC_ISSUER`,
`ROSTERDOCK_OIDC_CLIENT_ID`, the secret by name `ROSTERDOCK_OIDC_CLIENT_SECRET`). The board discovers the
endpoints from the issuer, records a state, a nonce and a PKCE verifier in `oidc_logins` (so any replica
finishes the flow), sends the browser to the provider, and on the callback exchanges the code server to server
(the secret as HTTP basic auth or in the form, never in a URL), verifies the id_token's signature against the
provider's JWKS, its issuer, audience, expiry and nonce, and keeps only the subject, email and name. A user is
found by subject, then by email (an owner invited them before they ever signed in, so their memberships
exist), else created. `ROSTERDOCK_OIDC_ALLOWED_DOMAINS` narrows who may sign in at all. Nothing from the
provider is stored beyond the subject; the login attempt is consumed on the callback.

## Drift and pools

Drift is a teammate against their own history, never against another teammate or a fixed number. After
a task run ends, its tokens and its duration are compared with the teammate's last thirty finished task
runs: beyond three median absolute deviations and at least one and a half times the median is a
departure. After a review decision, the rate of send-backs over the author's last ten decisions is
compared with the rate before: half or more, and thirty points up, is a departure. Each departure is one
`teammate.drift` event per metric per day, recorded by Peter with the run or review it came from; the
notifier pushes the sentence, Activity shows it, the teammate's page carries the line for a day, and
`GET /teammates/:id/baseline` has the numbers. Nothing stops: a person decides what to make of it.

Sandbox network policies per department are worker pools. The operator declares fleets in the chart
(`worker.pools`), each with its own network policy: what the pool's pods may reach besides the board and
Postgres, down to nothing. A department's sandbox names the pool; its tasks' runs go on that pool's
queue and only that fleet takes them. The default fleet keeps the M6 default policy (public HTTPS, no
private ranges). Departments without a pool run on the default fleet.

## Costs as files

Every run's usage is one CSV line (`/costs/export.csv`), for a budget window or a calendar month, with
the names a finance person needs (task, teammate, department, project, client, chargeback tag, model) and
the cost priced with the table as it stands now. The monthly report (`/costs/monthly`) is the same usage
for one calendar month grouped by project, and projects rolled up by their chargeback tag (untagged ones
under `null`, last), plus department, teammate, model and day; seats are the monthly seat price of every
teammate on the roster, not pro-rated. `/costs/monthly.csv` is the chargeback table: one line per project
with its tag, ready for an invoice. Tags live on the project (`chargebackTag`) and are optional.

## Templates as files

A company's shape is one JSON document: `company` (a title and the template name), `teammateTemplates`
(the company's own, by name), `teammates` (each by name with a role, engine, model, persona, playbooks and
toolbox, or a `template` name the missing fields come from) and `departments` (write policy, sandbox, a
lead and members by teammate name); since the backlog also `connections` and `clientPolicies` by
name. Export writes it from the company as it stands; import creates what
is missing and skips what exists (by handle for teammates, by slug for departments, by name for
templates), resolves leads and members by name, drops toolbox grants on connections the company does not
have, and says all of it in the report. The whole file goes through `assertNoRawSecrets` before anything
is read, so a persona or a playbook that carries a credential value is refused with nothing created.
`deploy/templates/gtm-company.json` and `finance-department.json` are the shipped examples and are
imported by the tests.

## The done criterion

Someone who is not the author installs from `docs/install.md` into a clean cluster and runs the M4 demo
there. The pieces that make it possible: the chart installs against any Postgres with every credential
by Secret name; `deploy/scripts/smoke.sh` is the install in one command on a laptop cluster; sign-in is
the operator's provider; the guides say what to do the day after. Run here against Docker Desktop's Kubernetes, twice. The smoke script installed the release with
network policies on; a demo driver (the same calls the pages make) signed in, created GTM Studio, hired
Ricky, Brody and Stubby on the stub engine, handed Peter the digest goal, and watched: Peter planned
three tasks by heuristic (no key on that board), started the research task, the worker in the cluster
claimed it, ran the stub, shipped three artifacts, completed with 1,500 tokens, the task moved to Review
and round 1 opened; Activity has the 21 events in order. The second run was on the M6 images after
`helm upgrade`: the board applied migrations 0014 to 0017 on boot, `/api/auth/providers` and the monthly
cost report answered, and `/metrics` counted the runs, the events and the tasks by status. Two things the
cluster taught: an upgrade from the M5 chart failed once on the worker Deployment's selector (a pool
label had been added to an immutable field; the default fleet now keeps its old selector), and a
re-install with the same image tag rolled nothing, so the smoke script now stamps a build-time pod
annotation.

## Demo script

Offline (the tests are the demo path): `pnpm test`. `oidc.test.ts` signs in against a fake provider
(discovery, JWKS, PKCE, a rotated key, every refusal); `templates.test.ts` exports a company and imports
it into another and imports the shipped files; `costs-export.test.ts` writes the CSVs and the monthly
report by tag; `metrics.test.ts` scrapes the board after a run; `tracing.test.ts` posts a run's trace;
`drift.test.ts` raises a departure on cost, duration and rejections and refuses to repeat itself;
`pools.test.ts` routes a department's runs to its pool's queue; the worker tests sample a cgroup and post
the worker's half of a trace.

On a cluster:

```bash
deploy/scripts/smoke.sh                        # Docker Desktop, kind (KIND=1), k3d, minikube
kubectl -n rosterdock-smoke port-forward svc/rosterdock-web 8080:80
```

Then the demo in `docs/install.md`. For the M6 pieces themselves: Settings, Templates, Export as a file
and Import a file; Costs, Monthly report and the CSVs; `curl localhost:3000/metrics` through a
port-forward to the board; a department created with "Runs on: secure" against a chart with
`worker.pools[0].name: secure`; Activity after a run that cost far more than the teammate's usual.

## Decisions taken while building

- No SDKs for the deployable pieces: OIDC is discovery, PKCE and JWS verification with `node:crypto`;
  traces are OTLP/HTTP JSON built by hand; metrics are a small registry in the text format. Each is a
  few hundred lines, fixture-tested offline, and adds nothing to the images. The trace id is the run's
  uuid and the root span id derives from it, so the board and the worker post their halves without
  talking to each other.
- Drift is a teammate against their own history (median and MAD of their last thirty runs; their own
  rejection rate before and after), never against a fixed number or another teammate, and never a gate.
  Peter is the observer on the event.
- Sandbox network policies per department are worker pools: a NetworkPolicy selects pods, so a
  department with a narrower network gets its own fleet and its own queue. The board routes at enqueue
  time and the run remembers its queue.
- The worker samples its cgroup rather than the board reading the metrics API: no cluster credentials on
  the board, and the number includes the engine child.
- The chargeback tag is a plain string on the project and the monthly report groups by it; a cost-centre
  table would be a second thing to keep in sync.
- The default fleet's Deployment selector stays exactly what it was in M1: the pool label lives on the
  pod template and on the pool Deployments only, because a selector is immutable and an upgrade must
  apply.

## Not in M6 (by design)

- Object storage for artifacts over 512 KB (the values and env exist; the client is in the backlog).
- Sign-out at the provider; `/metrics` behind a bearer; pod metrics from the metrics API; traces for
  Peter's model calls; drift thresholds from Settings; a per-pool engine image; the smoke script in CI.
- Codex as an engine (open since M2), and the rest of `docs/backlog.md`.
