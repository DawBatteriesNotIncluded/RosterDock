# Milestone 5 notes: governed tools

What landed, how an approval moves, what the done criterion means in the tree, and what is deliberately left
for later. The plan card: MCP connections added by URL or from a catalog with tool discovery and read/write
classification, credentials by name; tool modes per teammate, department policy and project client policy
narrowing, a broker that enforces before any network call; approvals with the proposed payload bound by
sha256, approve executes the bound bytes, reject re-plans; the Approvals view and Needs-you notifications.
Done when a write reaches a live system only with a matching hash on an approved record.

## Connections and toolboxes

A connection is an external system the board can reach: an MCP server over HTTP or stdio (an OpenAPI service
arrives in the next slice), named the way toolboxes name it (`hubspot`, `slack`). It is added from the
catalog, which fills the transport, an example endpoint and the env var NAME the credential lives under, or by
URL or command. Credentials are names: the board reads the value from its own environment at call time,
sends it as the bearer header (HTTP) or hands it to the child process (stdio), and scrubs it from any error.
Nothing on the row, in an event or in a response carries a value; a value where a name belongs is refused by
the raw-secret guard.

Discovery is `tools/list` against the live server. Each tool is classified: the server's `readOnlyHint` wins,
then the catalog's known reads and writes, then a name that starts with a reading verb (`get_`, `list_`,
`search_`); anything else is a write. A person can reclassify a tool and their word survives the next
discovery. Until discovery, a connection from the catalog carries the catalog's lists. A person can also
switch one tool off on the connection (`tools: [{name, off: true}]`): it is refused for every teammate
whatever the toolbox grants, an approval already pending on it is not sent, the pack lists it as switched
off, and the flag survives discovery. Policy still only narrows: there is no per-teammate tool matrix.

A teammate's toolbox is `[{connection, mode}]` with mode `off`, `read` or `ask`; it is the ceiling and only
a person sets it. A department with write policy `readonly` caps every connection at `read` for its tasks. A
project's client policy caps per connection (`caps`) or for every connection (`default`). The effective mode
is the narrowest of the three, and `effectiveMode` says which layer narrowed it, so the pack and the UI can
explain.

## OpenAPI connections

A service with no MCP server is reached the same way. `POST /connections/openapi/preview` with a parsed
OpenAPI 3.x document lists its operations (those with an operationId) classified by method. `POST
/connections/openapi` with the spec, a base URL, the credential's env var NAME and an allowlist of
operationIds registers a connection of kind `openapi`: the manifest (operations, auth header and scheme,
time and size caps) is stored on the row, and the operations are the connection's tools, named by the
operationId in snake_case. Nothing outside the allowlist exists. GET and HEAD read; every other method
writes; an operation can be forced to a write (`writes`) and never to a read. The broker calls
`{pathParams, query, body}`: path parameters must be scalars and all present, the body goes only with a
writing method and is capped, the answer is capped and redacted, a failing service yields its status line
and never its body.

## How a tool call moves

1. The worker still starts an engine with one MCP server, the board's. A teammate that wants a live system
   calls `board_tool_call` with the connection by name, the tool, and the arguments. `board_list_tools`
   tells it what it holds on this task: every connection in its toolbox with the effective mode, why the mode
   is narrower than granted (the department is read only; the client allows reads only), and a verdict per
   tool: run, propose or refuse. The pack says the same under "Your tools".
2. The broker resolves the connection (unknown: refused), the teammate's grant (not in the toolbox: refused;
   switched off by a person: refused), and the tool's classification (a discovered connection knows its
   tools and refuses names it does not have; a catalog-seeded one classifies by the catalog and the name).
3. A read runs now through the board's MCP client with exactly the arguments given; the answer comes back
   with secret-shaped keys redacted, and `tool.called` records connection, tool, task, teammate, the argument
   keys and whether it succeeded. Never the values.
4. A write under `ask` needs a title and a reason, then becomes an approval (see below). The same bytes
   proposed twice are one approval and the teammate is told to stop proposing. A write under `read` is
   refused with the reason and the connection never hears of it.
5. Approve hands the approval to `brokerExecutor`: the connection by id (or by name if it was re-added),
   enabled, and `tools/call` with the bound payload as the arguments. A connection that is gone, off,
   unreachable or refusing records `failed` with the reason. A connection with a pending proposal cannot be
   removed.

## How an approval moves

1. A teammate in a run proposes a write: the connection by name, the tool, the exact arguments, a title in
   manager language and a reason. The board stores the arguments with their sha256 (canonical JSON), emits
   `approval.proposed`, and parks the task: Blocked, "Needs your approval", `waitingOn` the approval. The
   same bytes proposed again while the first waits are the same row. The run should finish (hand over);
   when it does, `completeRun` sees the pending proposal and leaves the task at the gate with no review.
2. The Approvals view lists the company's proposals, pending first. Each card is the exact action: who asks,
   from which task, why, the connection and tool, the payload as JSON, the hash prefix. Owners and admins
   decide; everyone else reads.
3. Approve records the decision (`approval.approved`, with an optional note), re-hashes the stored payload
   and refuses to send when it no longer matches (`approval.failed`, "nothing was sent"), otherwise hands
   exactly those bytes to the executor (the broker) and records `executed` with the redacted answer or
   `failed` with the reason. Then, if no other proposal on the task still waits, the proposer is started
   again with a dispatch note and the outcome under "Approvals on this task" in their pack. When they cannot
   be started (engine off, budget), the task goes back to To do.
4. Reject records the note (`approval.rejected`). Nothing is sent; the task stays blocked. Peter's loop wakes
   on the event and re-plans the task: a note that repeats the rejection and says not to propose the same
   write again (the model reads the same context), `tasks.replans` goes up, the assignee starts again with
   the note in the pack. After `MAX_REPLANS` the goal turns amber as for any failure.

## Needs-you notifications

A person should not have to watch the board. Every event that needs one (`approval.proposed`,
`approval.failed`, `goal.questions`, `goal.escalated`, `pr.opened`, `pr.failed`, `budget.alert`,
`draft.proposed`) is pushed as it lands, once per event per process, to a webhook as one sentence in manager
language plus the event type and subject; a Slack incoming webhook renders the sentence as is. The target is
deployment configuration: the board's `ROSTERDOCK_NOTIFY_WEBHOOK_URL`, or per company the env var NAME the
owner puts in Settings, resolved where the board runs at send time. A name that is not set means no push and a
warning in the log, never a guess. The URL, which may carry a token, is never stored, never logged and never
in an event; `notify.sent` records only the event type and the name the URL came from. "Send a test" in
Settings posts one line so the owner knows the name resolves. One message per event whatever the number of
replicas: since the backlog, a notifier claims the event in `notify_claims` before sending.

## The done criterion

A write reaches a live system only through `brokerExecutor`, which is called from exactly one place,
`approveApproval`, after the stored payload has been re-hashed and compared with the sha256 it was proposed
with. `callTool` never calls a write itself: a tool classified as a write is proposed or refused. The board's
MCP client and the OpenAPI runtime are reached only from `callConnectionTool`, whose two callers are the
broker's read path and the executor. `approvals.test.ts` tampers with a stored payload and shows nothing is
sent and the row is `failed`; `broker.test.ts` and `openapi.test.ts` show the bytes the fake service
received are the bytes on the approved row, with the credential arriving by name as a header; the worker
still starts every engine with the board as its only MCP server (`--strict-mcp-config`), so there is no other
door.

## Demo script

Offline (the tests are the demo path): `pnpm test`. `approvals.test.ts` proposes, approves (the executor
gets exactly the approved bytes), tampers (nothing is sent), rejects (Peter re-plans with the note in the
next pack), and waits for two proposals before the teammate continues; `connections.test.ts` adds HubSpot from
the catalog, discovers its tools against recorded JSON-RPC over HTTP and a stdio fixture replayer, and shows
the credential travelling by name; `broker.test.ts` runs a read, refuses a write under `read`, proposes under
`ask`, and narrows through a readonly department and a client cap; `openapi.test.ts` registers a CRM from a
spec and does the same through HTTP operations; `notify.test.ts` pushes a proposal to a webhook as one
sentence; `stub-tools.test.ts` (worker) has the stub engine propose a write through the board like any engine.

Live, with the dev stack and no model:

```bash
pnpm db:migrate && pnpm dev            # board + web; Peter's loop runs every 30 s
pnpm dev:worker                        # the stub engine needs no key
```

1. Settings, **Connections**: add `n8n` from the catalog with the local n8n MCP URL (`http://localhost:3001/mcp`)
   and the credential NAME it uses (set that name in `apps/board/.env`), then **Discover**: the tools appear
   classified, workflow creation and activation as writes. Add `hubspot` by URL with a made-up endpoint too;
   it will refuse at execution time, which is a demo of `failed`.
2. Teammates, **Stubby** (a stub-engine teammate): Toolbox, `n8n` at "Reads, writes ask". Save.
3. Board, new task for Stubby in a project: brief "Inspect the workflows. [stub:tool n8n list_workflows]".
   Start it. The run's handover says "Called n8n · list_workflows; answer: …" and Activity has "Stubby read
   n8n · list_workflows". Nothing waited: a read runs.
4. New task for Stubby: brief "Draft the digest workflow. [stub:tool n8n create_workflow {\"name\":\"Digest
   (draft)\",\"active\":false,\"nodes\":[],\"connections\":{}}]". Start it. The task goes Blocked, "Needs your
   approval"; the sidebar badge counts one; Activity says "Stubby asks approval to stub write: create_workflow
   on n8n (n8n · create_workflow) for #N"; the webhook, if one is configured, got the same sentence.
5. **Approvals**: the card shows Stubby, the task, why, the exact action as JSON and the hash prefix.
   **Reject** with a note: nothing is sent; within a pass Peter re-plans the task and the next run's pack carries
   "rejected: your note". Start another such task and **Approve and run**: the write goes to n8n as exactly
   those bytes (a draft, inactive), the card says "Approved · executed", the task is back In progress and the
   restarted run reads the outcome under Approvals on this task. With the made-up `hubspot` endpoint instead,
   the card says "Approved · failed" with the reason and nothing else moves.
6. Departments: set Stubby's department to Read only and repeat step 4: the broker refuses the write with
   "the … department is read only" and the handover says so; nothing is proposed. Settings, **Client
   policies**: cap `n8n` at Off for the project and repeat step 3: "n8n is off for this task".

### What the demo showed

Run offline (226 board, shared, web and worker tests before the stub marker; 229 after). The live script
above was written and not executed against a live n8n: reads are safe, and a `create_workflow` with
`active: false` is a draft, but a write to a live system is a person's decision.

## Decisions taken while building

- Every external call has one door, `callConnectionTool`, with two callers: the broker's read path and the
  approval executor. A third caller is a bug by construction.
- The stub engine proposes writes like any engine would, through `board_tool_call` over the run's MCP token,
  so the gate can be demonstrated without a model. It is a marker in the brief, not an engine feature.

- The update schemas for teammates and projects were `partial()` of the create schemas, and zod keeps the
  create defaults under `partial()`: a PATCH that named one field reset the others (engine, persona,
  playbooks, client, branch) to their defaults. The web sent every field, so nothing showed until the
  toolbox column arrived and a rename would have emptied it. Both update schemas are now explicit, with no
  defaults; a test renames a teammate and a project and checks the rest survives.

## Not in M5 (by design)

- Email as a notification target: the webhook is the one target (a Slack incoming webhook works as is); an SMTP
  target by name is in the backlog. Cross-replica dedupe of notifications (both landed from the backlog).
- OpenAPI specs in YAML; MCP OAuth flows (the credential is a bearer by env var name); caching a stdio client
  per connection (a child is spawned per call); a connection health check in Settings.
- Approvals from the Board drawer, and the Office desk counting approval rows rather than blockers.
- The `auto` tool mode from the plan (a write that executes without a person). It contradicts "human gates
  only for merges and live external writes" and was dropped; modes are `off`, `read`, `ask`. If a sandbox
  target ever needs it, it would be a per-connection flag ("not live"), never a teammate mode.
