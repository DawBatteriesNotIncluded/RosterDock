# Milestone 3 notes: review

What landed, how a review moves, what the done criterion means in the tree, and what is deliberately
left for later. The plan card: a review object from a run's diff (files, hunks, comments anchored to
file, hunk and line); a reviewer teammate that reviews through the board MCP with humans able to do
the same and veto; request changes that requeues the author with the comments in the pack; approve
that marks Done and opens a pull request; checks (secret scan, declared outputs, the repository's
tests, evaluation against weighted criteria). Done when a task cannot reach Done by any route except an
approved review.

## How a review moves

1. The assignee's task run completes. In the same transaction the board parses the run's `changes.diff`
   artifact into files and hunks, opens the task's review (or advances it to the next round), runs the
   checks, and picks a reviewer: a teammate whose role says reviewer, verifier or QA, from the task's
   department first, never the author. No such teammate: the review waits for a person.
2. The reviewer teammate gets a run of kind `review`. Its pack has "Your review": the diff inline, the
   checks so far, earlier comments (marked by round), and the five review tools. A review run never
   moves the task; the decision tools do.
3. Comments anchor to a file, a hunk index and a line (new-side, or old-side for a deleted line); the
   board refuses anchors that are not in the current round. Scores against the task's weighted
   criteria become the evaluation check.
4. Request changes: the review waits with `changes_requested` and the author gets a new task run whose
   pack has "Changes requested (review round N)" with the summary and every comment. When that run
   completes, round N+1 opens with a fresh diff, fresh checks and a fresh reviewer run; earlier comments
   stay visible, labelled by round.
5. Approve: the task is Done (`tasks.done_by` records the review, round and approver), and for a
   GitHub project whose run recorded a base sha a pull request is proposed (payload plus sha256) and
   executed right after commit: the reviewed diff is applied to the base commit through the Git Data
   API and a pull request opens on `rosterdock/task-N`. Merging needs a person. No token, no repository or
   no base sha: still Done, no pull request. A GitHub failure is recorded on the pull request and
   announced as `pr.failed`.
6. Veto (owners and admins, on an approved review): the task goes back to In review with the note;
   an opened pull request is closed with the note as a comment (since the backlog), the branch left
   for a person.

Who may decide: never the author; a teammate only as the assigned reviewer; a person with the
reviewer, admin or owner role. Anyone who can post may comment. Viewers read.

## The done criterion

`tasks.status = 'done'` is written in exactly one place, `approveReview`. The move route refuses
`done` for everyone (409), the shared `MoveTaskSchema` does not admit it, no board tool sets it,
`completeRun` moves a task to review, blocked or todo only, and a veto is the only thing that takes
a task out of Done. `reviews.test.ts` walks every refusal: the author's own approve, a non-reviewer
teammate, a viewer, a second approve, moving a Done task.

## Demo script

Offline (the tests are the demo path): `pnpm test`. `apps/board/test/reviews.test.ts` runs Cody's run to
completion with the recorded diff, the Verifier reviews through the MCP client (diff, two comments,
scores, request changes), Cody's rerun carries the comments in its pack and opens round 2, the
Verifier approves, and on a GitHub project the pull request is opened against the recorded API shapes.

Live, with the dev stack:

```bash
pnpm db:migrate && pnpm dev            # board + web
pnpm dev:worker                        # only when you want real runs: about 200k tokens each
```

1. Hire a teammate whose role contains "reviewer" (the seed script and the tests call it Verifier).
2. Create a task for Cody with expected outputs and two or three acceptance criteria, and start it.
3. When the run finishes, Reviews shows the diff; the Verifier's review run starts on its own. Watch it
   comment and decide in the Run tab; or decide yourself: comment on a line with the + button, score,
   Request changes (Cody restarts with the comments) or Approve (Done; a pull request if the project
   is on GitHub and `ROSTERDOCK_GITHUB_TOKEN` is set on the board).
4. Veto the approval as the owner: the task is back in review.

Without a worker, the review can be seeded by running the worker protocol by hand: dispatch, claim
with the fleet token, post `changes.diff` and an output, complete. That is what the M3 chat did to
check the view against the dev company (task #9 in GTM Studio).

## Decisions taken while building

- One review per task, advanced in rounds, rather than one review per run: the queue shows one card
  per task, comments keep their round, and "request changes" is a state of the same review.
- The diff is parsed once, at completion, and stored as hunks in `review_files`. Anchors are validated
  against those hunks, so a comment can never point at a line that is not in the round under review.
- Deletions were missing from the M1 diff (`git add -A -N` staged them away). The harvest now stages
  everything and diffs the index, without rename detection so every hunk applies to one path.
- The pull request is built without a checkout: the board applies the reviewed hunks to the exact base
  commit through GitHub's Git Data API. Binary files cannot ride a text diff, so a diff with one fails
  the pull request (the task is still Done). The proposal is bound by sha256 before execution, as every
  external write will be from M5.
- The reviewer teammate's approval opens the pull request. Merging is the human gate; opening is not.
- Test files run against one Postgres with 100 connections; the board's pool and the queue's pool are
  now sized from `ROSTERDOCK_DB_POOL_MAX` (3 in tests) and the board's vitest runs at most 6 files at once.
- GitHub fixtures are response shapes from the REST API documentation, not live recordings: there is no
  test repository to record against without a token. The provider's request bodies are asserted in full.

## Not in M3 (by design)

- Codex adapter (still open from M2), a per-teammate notification inbox, reviewer assignment from the
  UI (the role picks the reviewer), a split diff view, pull requests on hosts other than GitHub, pull
  requests for diffs with binary files, closing the pull request on veto.
- All of these shipped after M3: Codex, the inbox, reviewer assignment, the split diff, GitLab merge
  requests, binary files and closing on veto.
