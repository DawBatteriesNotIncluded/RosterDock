# Milestone 2 notes: teammates work together

What landed, what the real runs showed, and what is deliberately left for later.

## Board MCP server (M2-1)

- `POST /api/mcp`: a stateless Streamable HTTP MCP server, authenticated with the run-scoped bearer token only. A fresh server and transport per request, so the board stays horizontally scalable.
- Tools, all acting as the teammate the token belongs to: `board_read_task`, `board_list_my_tasks`, `board_post_message`, `board_create_task`, `board_set_blocker`, `board_request_review`, `board_log_decision`. Every input passes the raw-secret guard before it is stored.
- The worker writes a private MCP config file per run and starts Claude Code with `--strict-mcp-config --mcp-config <file>`; `mcp__rosterdock` is on the allowed-tools list. Claude Code loads the tools lazily through `ToolSearch`, which costs one extra model call per run.
- Verified with a real haiku run (task #6): read task → post message mentioning @ricky → log decision → write file → request review. 231k tokens, 29 s. Most of the tokens are the CLI's own system prompt, served from cache.

## Turns, answers and chasing (M2-2)

A **turn** is a run of kind `turn`: a teammate answering a mention on a task that is not theirs. The task's status, assignee and active run do not change when a turn starts or ends. The pack for a turn opens with "Your turn", quotes the ask, names the assignee, and tells the teammate to answer with `board_post_message` and not to take the task over.

Routing happens after every posted message (REST or board tool):

1. If the task is blocked waiting on a teammate and that teammate is the author, the assignee is restarted with the answer in the conversation (`runs.trigger_message_id` records which message did it). If the assignee is a person, the task goes back to To do.
2. Each mention becomes a turn for the named teammate, unless a filter says no.

Filters, in order:

- A teammate mentioning itself routes nowhere.
- **Reply depth**: a message remembers the run it was written in (`messages.run_id`). Question → answer → follow-up → answer, then the chain stops (`MAX_REPLY_DEPTH = 3`). A person's message starts a new chain.
- **Turn cap**: 6 turns per task per hour, whoever asks.
- **Restart cap**: an answer restarts a blocked assignee at most twice per task per hour. After that the task stays blocked, with the answer in the conversation, until a person weighs in.
- The assignee never gets a turn on their own task: an answer restarts them (rule 1), or the message waits for their next run.
- A teammate already live on the task is not woken again; the message is in their conversation and `board_read_task` shows it.

Tasks a teammate files for a teammate (via `board_create_task`) start on their own. `board_set_blocker` with `waitingOnHandle` posts the ask on the task, so the waited-on teammate gets a turn and the answer has a place to land. The REST task and message routes do not auto-start anything: a person may be drafting.

**Chasing.** Every `ROSTERDOCK_CHASE_INTERVAL_MS` (60 s) the board looks for tasks blocked on a teammate for longer than `ROSTERDOCK_CHASE_BLOCKED_FOR_MS` (10 min) and not chased in the last 6 h. The company's project manager teammate (handle `peter`, or role containing "project manager") posts "@handle #n is waiting on you: …" on the task, which gives them a turn, and a `task.chased` event lands in Activity. No manager teammate, no chasing.

### What the demo showed

Ricky's task: ask @cody one question, file a task for him, write a plan, request review. Two workers.

- Ricky asked, Cody got a turn on Ricky's task while Ricky was still running: two runs at once, as required.
- Ricky filed #8 for Cody; it started on its own and Cody worked it while his turn on #7 was still open (the live index is per task and teammate).
- #7 reached review with no human input. #8 could not: neither teammate had a source for the credential names, so Cody blocked on Ricky, Ricky answered "I don't know either", the answer restarted Cody, and the pair went round three times before stopping. Ten runs and 2.3M tokens for a question nobody could answer.

That loop is what the restart cap now closes: after two restarts the task stays blocked for a person. The behaviour itself was right (nobody fabricated credential names, both logged why they were blocked); the cost was not.

### Costs to keep in mind

- A haiku run through the CLI costs about 200k tokens whatever it does, because the CLI's system prompt and tool catalogue are sent every call. Turns are as expensive as task runs. Cache reads are most of it.
- Two workers doubled throughput with no board changes; the queue and the claim-time takeover were built for it in M1.

## Costs, prices, live panel, autoscaling (M2-3)

- `GET /api/companies/:id/costs?window=day|week|month` builds the cost report from `run_usage`: totals, forecast (spend so far divided by the elapsed fraction of the window), the company budget, and lines by department (with the department budget), project, teammate and model. Seat billing is computed alongside: a `model_prices` row with `seatPriceMonth` matches a teammate by model, or by engine (`claude_code`, `codex`), pro-rated to the window. Money comes from the price table as it stands now, so a price set after a run still prices it (the run itself keeps the cost recorded at completion). Lines show a dash when no model in them has a per-token price; tokens are always counted.
- Costs page: window and billing toggles, four cards (spend so far, budget, forecast, "if billed the other way"), 14-day token bars, and the four tables. Rows open the teammate or the project's board. It refreshes when an event lands.
- Settings: the price table (per million tokens, or per seat per month) and budgets per scope and window, editable by owners and admins. A note that secrets are names only.
- Working now: a panel at the top of the Company view's rail listing every queued, running or interrupted run with the teammate, the task, the current step, elapsed time and tokens so far. Polled every 3 s while something runs; refreshed on run events otherwise. Turns read "answering on".
- `GET /runs?status=a,b` takes several statuses.
- Helm: `worker.autoscaling` renders a KEDA `ScaledObject` on the worker Deployment with a PostgreSQL trigger counting unfinished jobs on the `runs` queue (one worker per waiting run, between min and max replicas, 120 s cooldown). Off by default; needs KEDA in the cluster. Pod CPU and memory in the live panel wait for M6.

## Office view v1 (M2-4)

Ported from the prototype's office, fed by real data. Nothing is stored: the view is a projection of tasks, the last 100 events and the live runs the Company view already polls. (Since the backlog, where the rooms and desks stand is stored in the company settings; what they are is still derived.)

- **Pixel office**: a canvas with a room per department (and one for teammates in none), a desk per member, and a sprite per teammate. Screen on and hands moving means a task run is live; a paper means reading, answering a turn or reviewing; a red "!" means blocked; an amber "?" means waiting on an approval, and the sprite walks to your desk. Idle sprites wander their room. Handoffs travel as packets along arcs and land as speech bubbles. Click a room to zoom to it, a teammate to open their task, your desk for approvals.
- **Interaction map**: an SVG with a column per department, a ring colour per teammate for what they are doing, and arcs for handoffs (task filed, mention or answer, approval, blocked). Rendered server-side in tests.
- **Handoffs in flight** come from: tasks a teammate filed for another teammate, blocked tasks waiting on a teammate, approval blockers (to you), mentions in recent `message.posted` events, and live turns.
- Approvals and reviews arrive in M3 and M5; the office already has the edge kinds and the desk for them.
