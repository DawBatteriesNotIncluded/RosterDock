RosterDock

RosterDock is an AI company platform. This is what we are building, why the current repo is not the base, how the new system is shaped, and the milestones that take it from an empty repository to a Helm chart a customer can install.

What we are building

A self-hosted platform that lets an organisation run an AI company. The operator describes the company as departments staffed with AI teammates. Each teammate is three things: a brain (a model on an engine such as Claude Code or Codex), a persona (a written job description and playbooks), and a toolbox (a governed set of MCP servers). The operator hands the company goals. A project-manager teammate splits goals into tasks on a shared kanban. Teammates work in parallel, message and delegate to each other, and review each other's output at the level of individual diff hunks. Humans are pulled in at exactly two points: merging finished code, and any write to a live outside system.

It runs on Kubernetes. The board is a stateless service, workers are pods that scale with the queue, and the whole thing ships as a Helm chart that a customer installs into their own cluster with their own model accounts and secrets. No data leaves their network.

What it is not. It is not a coding agent, a git host, or a chat assistant. It is the layer that turns coding agents and research agents into a team you can watch, steer and trust, and it plugs into the git host and the MCP servers a company already has.

Why not the current repo

The current repo is a governed, human-in-the-loop control plane. Its defaults are the inverse of this product: kill switch on, report-only level, a human owns every Done. It has no messaging between agents, no agent-created tasks with real identity, no diff capture, no review object, no roles, and no project-manager loop. In three months of live use it produced zero completed tasks. The parts that are genuinely good are carried over; the shape is not.

A day in the product

  1. You open the company. Departments show who is working, who is blocked, and what is waiting on you.
  2. You type a goal: "Send a weekly digest of Gong calls with next steps to #sales every Friday."
  3. Peter, the project manager, splits it into four tasks across Research and Engineering, assigns them, and opens a project. The cards appear.
  4. Ricky starts researching while Cody scaffolds the workflow. Cody hits a gap and asks @ricky on the task. Ricky answers and files a follow-up task for Cody.
  5. Cody pushes. The Verifier reviews the diff hunk by hunk and requests one change. Cody fixes it and resubmits. The Verifier approves.
  6. The approval opens a pull request. Merging it is yours. Activating the workflow in n8n is a separate approval card showing the exact action and the credential name.
  7. Peter watches all of it. A failed run gets re-planned. A stuck task gets chased. You only hear about the two gates.
  8. The Office view shows the whole thing happening: teammates at desks, handoffs moving between rooms, an amber question mark walking to your desk.

Peter, in three roles

Peter is not a form. He is a teammate whose tools are the board and the company itself, and he is present from the first minute of a new install.

1 · Company architect

"I need a finance function that reconciles Xero weekly" or "staff a research agency for client X". Peter proposes departments, teammate templates with personas, the MCP toolbox each needs and the write policy, as a draft you edit and accept. Accepting creates the org. He can also audit an existing company: idle teammates, missing reviewers, toolboxes wider than their department policy.

2 · Intake planner

The v1 Peter, kept: a goal becomes a validated pack with background, required outcome, acceptance criteria, required artifacts, done definition and open questions. He asks at most a few clarifying questions, then hands off explicitly. Handoff opens a project and its tasks.

3 · Project manager

After handoff he stays on. He watches runs, reviews and budgets, re-plans on failure, chases blocked tasks, rebalances load between teammates, and escalates only at the two human gates. Department leads are Peter instances scoped to their department; the company Peter routes to them.

All three run on the same loop: board code that decides what to do and asks the model one structured question per decision (a plan, a re-plan note, an org draft), with a heuristic when no model is configured (docs/m4.md). The architect's proposals (departments, teammates, toolboxes, policies) are always drafts a human accepts. Peter never grants a tool to anyone by himself.

Rules that never soften

  • Autonomy by default. Teammates act without asking. Human gates exist only for merges to protected branches and writes to live external systems.
  • Secrets are names. The platform stores env-var names and secret refs, never values. Values resolve inside worker pods from the cluster secret store. A raw-secret guard rejects writes that look like values. One door lets a person set a value from Settings: it goes write-only into the secret store under the company and the name, never into a row, an event or a response, and that company's connections resolve it before the board's environment.
  • External writes are proposed, approved, executed. With hash binding. Drifted bytes are rejected and audited.
  • Teammates never mark Done. A review approval does, and that can come from a reviewer teammate. Humans can veto any review.
  • Policy only narrows. Teammate toolbox sets the ceiling: a connection with a mode, optionally only some of its tools; department policy and project client policy can only tighten it.
  • One event stream. No visualisation-only events. If the office shows it, the audit log has it.
  • Roles from day one. Owner, admin, reviewer, viewer, teammate. Every mutating endpoint checks one.
  • Offline tests. The suite never needs a model, a git host or an MCP server. Protocol adapters are tested against recorded fixtures, not hand-written echoes.

Architecture

Board API

Node 22, TypeScript, Fastify. Owns all state, the event stream (SSE), the queue producer, the review and approval engines, and the broker. Stateless; scales horizontally.

Web UI

React, Vite, Tailwind, shadcn. The prototype's design system. Views: Company, Board, Reviews, Approvals, Activity, Office, Departments, Teammates, Settings.

Worker

Separate image. Claims a run from the queue, checks out a worktree on an ephemeral volume, runs the engine headless with the persona pack and a run-scoped board token, streams events, captures artifacts and the diff, exits. Killed workers are reaped and the task requeued.

Engines

One runner adapter interface. Claude Code and Codex ship; OpenCode is in the backlog. Each is a table row, not a copy of the code.

Board MCP server

The tools teammates use to act on the board: read task, post message, create task, request review, propose action. Scoped by run token. This is how agents talk to each other.

Tool broker

Proxies external MCP servers. Applies tool modes and policies. Reads pass through; writes under ask become approval records and execute only once approved; read refuses writes and off refuses everything, before any network call.

PM loop

Peter is a board loop that runs on a schedule and on events, with one structured model call per plan, re-plan or draft. Plans, assigns, watches, re-plans, escalates at gates.

Storage

Postgres for everything relational and the event log. pg-boss for the queue so day one needs no Redis. S3-compatible object storage for artifacts and diffs, MinIO locally.

Git

Provider interface. GitHub and GitLab: clone, push branch, open a pull or merge request, read checks. OneDev later.

Deploy

Docker Compose for local. Helm chart for production: board Deployment, worker Deployment with HPA on queue depth, Postgres and MinIO as optional subcharts or external, OIDC for login, External Secrets compatible.

Milestones

Each milestone ends with a demo you can click and a green offline test suite. Work is committed in small slices on main. Durations assume one focused engineer plus agents; treat them as order of magnitude.

M0

Foundation · weeks 1 to 2

  • New repo, license, CI (build, lint, test), Docker Compose with Postgres and MinIO.
  • Schema and migrations for companies, users, memberships, departments, teammates, projects, tasks, messages, events.
  • Auth: OIDC login plus local dev login; roles enforced by a single guard.
  • Event stream: append, replay from seq, SSE endpoint.
  • React shell with the prototype's tokens: Company, Board with Blocked, Departments matrix, Teammates editor. Static data replaced by the API.
  • Teammates as first-class accounts: every author, assignee and reviewer field accepts a user or a teammate; the same role guard applies to both.
  • Helm chart skeleton that deploys the board against an external Postgres.

Demo: create a company, a department, a project and a task in the UI; a second browser sees them appear live. Done when: every mutating route has a role check and an event.

M1

One agent works · weeks 3 to 4

  • Queue (pg-boss), run records, run-scoped board tokens.
  • Worker image: claim, clone and worktree on an ephemeral volume, run Claude Code headless with persona pack, stream events, capture declared artifacts and the diff to object storage, report usage.
  • Reaper requeues dead runs; task goes back to todo with a blocker note.
  • Task drawer shows live run log, outputs and tokens.
  • Budgets: token limits per company, department, project and teammate enforced at claim time; 80% and 100% alerts as events. Per-run cost line.
  • Sandbox presets, basic: filesystem and environment rules per department applied to the worker. Crash checkpoints with secrets sanitised, so a requeued run resumes.

Demo: assign a task to Cody; watch the run; open the produced files. Done when: killing the worker pod mid-run requeues the task without manual cleanup.

M2

Team collaboration · weeks 5 to 6

  • Board MCP server: read task, list my tasks, post message, create task for teammate, set blocker, request review, propose action.
  • Mentions route to the named teammate's next turn; agent-created tasks carry the creator's identity.
  • Parallel workers with per-task worktrees; HPA on queue depth in the chart.
  • Blocked semantics: dependency, waiting on teammate, waiting on approval; Peter's stub chases blocked tasks on a timer.
  • Decision audit trail: teammates log assumptions and confidence via the board MCP; shown in the task drawer.
  • Costs page per company: tokens and money by department, project, teammate and model; daily and weekly trend; spend against budget with a forecast to end of period; 80% and 100% alerts. Price table per model in Settings, with API per-token prices or a seat price for subscription CLIs, so a company can see exactly what running on API models would cost versus seats.
  • Live process panel per running teammate: current step, elapsed, tokens so far.
  • Notification filtering so teammates never wake each other in a loop; caps on tasks created per goal.
  • Office view v1 (pixel and map) rendered from real events.

Demo: Ricky asks Cody a question and files a task for him; both run at once; the office shows the handoff. Done when: two agents complete a two-task chain with no human input.

M3

Review · weeks 7 to 8

  • Review object from a run's diff: files, hunks, comments anchored to file, hunk and line.
  • Reviewer teammate (Verifier) reviews through the board MCP: comment, request changes, approve. Humans can do the same and veto.
  • Request changes requeues the author with the comments in the pack. Approve marks done and opens a PR through the GitHub provider.
  • Checks: policy scan for secret-shaped strings, declared outputs present, tests if the repo has them, and output evaluation against the pack's weighted criteria.

Demo: agent-to-agent review with one round of changes and a PR at the end. Done when: a task cannot reach done by any route except an approved review.

M4

Peter: PM loop, architect, and research · weeks 9 to 10

  • Peter as a board loop with structured model calls: intake, decompose with done definitions, assign by role and load, watch runs and reviews, re-plan on failure, escalate only at gates. Runs on events and on a schedule.
  • Research persona path: document artifacts with sources, a research review checklist instead of a diff.
  • Department leads as scoped PM instances; company PM routes goals to leads.
  • Recursion and cost caps per goal; Peter reports what it spent.
  • Peter as company architect: from a goal or a gap, proposes departments, teammate templates, toolboxes and policies as a draft you accept; audits an existing company for idle teammates and over-wide toolboxes.

Demo: one typed goal to a merged PR and a research document with no human touch except the merge. Done when: a run failure is re-planned without a human noticing.

M5

Governed tools · weeks 11 to 12

  • MCP connections: add by URL or catalog, tool discovery, read and write classification, credential by name.
  • Tool modes per teammate; department policy and project client policy narrowing; broker enforces before any network call.
  • Approvals: proposed payload, sha256 binding, approve executes the bound bytes, reject re-plans. Approvals UI and Needs-you notifications to Slack or email.
  • First real integrations: n8n, HubSpot, Slack, Xero.

Demo: Finn proposes invoice approvals in Xero; Cody proposes activating an n8n workflow; you approve one and reject one. Done when: a write reaches a live system only with a matching hash on an approved record.

M6

Deployable · weeks 13 to 14

  • Production Helm chart: values for external Postgres and S3, OIDC, secrets, resource limits, HPA, network policies for worker pods.
  • Company, department and teammate templates as importable files.
  • Costs export (CSV) and a monthly cost report per company; optional chargeback tags per project.
  • Observability: OpenTelemetry traces per run, Prometheus metrics, structured logs, pod CPU and memory per running teammate in the live process panel.
  • Behavioural drift detection: alerts when a teammate's cost, duration or rejection rate departs from baseline. Sandbox network policies per department.
  • Install guide, operator guide, security notes. A fresh cluster install in an afternoon.

Demo: install into a clean cluster from the chart and run the M4 demo there. Done when: someone who is not you does it from the docs.

Company model providers

After M6 · decided 2026-10-22

Until now every teammate thinks with the operator's own model keys. A company can bring its own model account instead, and choose for each teammate which account it thinks with. The board's own models stay the default: nothing about an existing teammate changes until someone picks a provider for it, and nothing is migrated.

What a company gets

  • Providers. Settings, Models holds the company's named providers, of five kinds: Anthropic, OpenAI, Azure OpenAI, Amazon Bedrock, and an OpenAI-compatible server (vLLM, Ollama, LiteLLM and the like). Each has its endpoint or region, its credentials by secret name, and the models it serves with their prices. Check lists the models the key reaches, and costs nothing. Owners and admins manage providers. Everyone in the company sees them by name and setting, and no one ever sees a value.
  • A key enters once. A person pastes it through the existing write-only door (PUT /secrets/:name), picks a secret the company already set, or uses a name the operator shares. The provider keeps the name only, and the page says when the value was set and by whom, never what it is.
  • A brain per teammate. Every teammate, Peter and the department leads included, picks a provider, then one of its models. The engine follows from the model: Claude models run on Claude Code, OpenAI models on Codex, so a teammate cannot be given a pair that does not run. "This board's own models" keeps today's engine and model choices exactly, and Peter's brain, picked on his page under Teammates like every teammate's, keeps today's choices under it. Settings, Models lists this board's own models (each CLI and the API key, and whether it works where the board runs) above the company's providers.
  • Costs by provider. A price belongs to a provider and a model. Without one the board uses the company's price for that model on the board's own models, then the Anthropic list price, and otherwise says "No price yet", never US$0.00. Costs gains a By provider table, both CSV exports gain a provider column, and the run panel names the provider. A company keeps one currency.

What the operator controls

  • ROSTERDOCK_MODEL_PROVIDERS (chart board.modelProviders) lists the kinds a company may add, and board in the same list lends the board's own models. Unset means all five kinds and board, so an upgraded board behaves as before and companies can bring keys at once. Without board, every teammate needs a provider, and Peter without one plans by role and says why. A board with an unknown entry does not start. Narrowing the list later deletes nothing; a provider of a kind no longer listed is refused, in manager words, when a teammate is saved, at dispatch, when Peter plans and at the gateway.
  • Private endpoints (an Azure private endpoint, a vLLM or Ollama in the cluster) need an entry in ROSTERDOCK_PRIVATE_DESTINATIONS, for every company or for one, and board egress to their port. There is no second list.
  • Workers need nothing new: a provider run talks only to the board. Upgrade the board first, then the workers, then give teammates a provider.

How a key stays on the board

  • No company key reaches a worker pod, a claim, a run spec, a pack, an engine's environment, a workspace, Postgres, an event or a log. Only the board reads a value, when it makes the call, and keeps it in memory for at most a minute.
  • An engine reaches its company's provider through a model gateway on the board, scoped to its run: /api/worker/runs/:runId/model/{anthropic|bedrock|openai}/…. It signs in with the run token it already holds. On every request the board checks the token, that the run is still running, the path and the model, then puts the company's credential in place of the token and streams the provider's answer back through the address guard.
  • The gateway is pinned to the run's provider and model. It allows only the paths the recorded engines send, refuses a request that came through the public ingress (nginx adds X-Forwarded-For, and also answers 404 on these paths), and replaces the provider's 401 and 403 bodies with its own words.
  • The engine's environment loses every model and cloud credential name (ANTHROPIC_*, OPENAI_*, CODEX_API_KEY, AWS_*, AZURE_* and the like) and gets a fresh config directory for the run. The run token is kept from the run's own commands: Codex excludes ROSTERDOCK_RUN_TOKEN from its shell, and Claude Code runs with CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1.
  • A worker older than the board cannot run a provider run. The claim carries features: ["model-gateway"]; a claim without it fails the run with "This board's workers are older than the board", so a company's model id never runs on the fleet's keys.
  • Peter plans from the board through small HTTP adapters: the Anthropic SDK, the Responses API, Bedrock InvokeModel, and Chat Completions for a compatible server without Responses. No CLI ever runs on the board for a company provider.

What remains, and why we accept it

  • A stolen run token spends that company's quota on the run's provider and pinned model, on the allowed paths only, until the run ends. It never reveals the key. Code in a worker pod can read a live run's token; binding a token to the pod that claimed its run is in the backlog.
  • Every worker pod holds the worker token and DATABASE_URL. With them, code could claim another company's queued run, or repoint a compatible provider's endpoint so the gateway sends the key to its own host. The other kinds' hosts are fixed or derived from the region, and checked again on every request. The endpoint seal and a worker database role limited to the queue close it, both in the backlog; until then, companies that must not reach each other use separate boards, as docs/security.md already says.
  • The board holds every company's keys, as it holds connection secrets today, and prompts and answers pass through its memory. Neither is stored or logged.

Risks and how we hold them

  • Token cost. A v1 Claude Code run measured around 100k tokens. Budgets at company, department and project level from M1, and Peter reports spend per goal.
  • Runaway loops. Two agents delegating to each other forever. Caps per goal on tasks created, runs, and depth; Peter cannot create tasks past the cap without a human.
  • Worker security. Worker pods run untrusted model output. Ephemeral volumes, no cluster credentials, network policy allowing only the board, the git host and approved MCP endpoints.
  • Protocol drift. v1 shipped three live-only bugs because tests echoed the adapter's assumptions. Adapters are tested against recorded real responses.
  • Scope creep. v1 grew 117 commits in one week and lost coherence. One milestone at a time; anything not in the current milestone goes on the list, not in the tree.
  • Docs rot. A route or concept lands with its doc line in the same commit, or it does not land.
