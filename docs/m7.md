# Milestone 7 notes: full autonomy

Planned with the owner (this repository's maintainer) on 2026-11-02; nothing here is built yet. Each slice adds what it builds to this file as
it lands, as M0 to M6 did. The plan card: a company runs itself. Peter staffs it, the team builds and reviews,
the board merges, and live writes run, with no person in the loop unless a rule puts one there. Done when a goal
goes from typed to merged with nobody touching it, on a team Peter chose and hired.

## Where it starts

Checked on `main` at `0b1a462` on the owner's Windows PC, 2026-11-02:

- The offline suite is green (shared 129, web 69, worker 188 with 6 symlink tests skipped without Developer
  Mode, board 425), and so are typecheck, lint, format and the web build.
- On the stub engine the README's goal goes from typed to done: Peter plans three tasks, a worker claims each
  within a second, and each moves to Done once its review is approved. That run opened no pull request, and no
  real model has yet taken a goal to a merged one.
- Peter designs a team only as a draft a person accepts (`apps/board/src/peter/architect.ts`), and a goal's
  plan can name only teammates already on the roster (`peter/plan.ts`).
- A review goes to the first teammate whose role text matches review, verif, QA or quality (`pickReviewer` in
  `reviews/service.ts`).
- Nothing pauses a company: a run stops alone (`POST /runs/:runId/stop`) or with the rest of its goal's runs
  (`POST /goals/:goalId/stop`). A spent budget refuses new runs at dispatch, and a running run carries on.
- The worker's heartbeat already reports the run's usage, and its answer carries `stopRequested` (`heartbeat` in
  `runs/service.ts`), so Pause and a budget that stops a run mid-way need no new channel.
- Claude Code's default tools leave out Bash (`ROSTERDOCK_CLAUDE_ALLOWED_TOOLS`). A change to a file with CRLF
  line endings cannot become a pull request, text that is not UTF-8 is corrupted on the way, and every file is
  written as mode 100644 (`CHANGELOG.md`, Known issues).
- The board never merges: every pull request it opens says "Merging needs a person".
- A teammate on a later review round can approve its own work; the fix is #80, open.

## The proof run

Slice 1, on 2026-11-02, on the owner's PC. A throwaway board and worker ran `main` at `0b1a462`, with Peter on
Automatic and two teammates hired by hand, since Peter cannot hire before slice 9: Maya, a Python engineer on
Claude Code with Claude Sonnet 5.5, and Theo, a reviewer on Claude Code with Claude Opus 5.5. The repository was
a copy of the owner's Tradie, a Python trading bot, as its working tree stood, cloned from a `file://` path. The
board opens no pull request for a repository on no host it knows, so the run ends at an approved review. The
worker allowed Bash; no keys reached the run, and the goal forbade running the bot and the tests marked
practice.

The goal: in Tradie's back-test, also report the longest losing streak and the worst single trade, in the
printed summary and in a summary CSV, with tests and a README line.

What happened, with nobody touching it:

- Peter planned through the Claude Code CLI, signed in on the owner's plan, in 22 seconds: one build task for
  Maya.
- Maya's run took 4 min 48 s and 381,752 tokens, most of them cache reads. It added
  `tradie/backtest/metrics.py` and its tests, the two lines in the printed summary, the summary CSV, and the
  README line.
- Theo's review run took 1 min 11 s and 377,063 tokens. He approved round 1 with a score of 0.97 and one
  comment that did not block, and the task and the goal were Done 6 min 15 s after the goal was typed.
- Checked afterwards by hand: the change applies to the copy, and Tradie's suite passes on it (95 passed, the 3
  practice tests deselected).

What broke:

1. **A run wrote outside its directory.** Making a virtualenv failed inside the run ("ensurepip"), so Maya ran
   `pip install -e ".[dev]"` with the PC's own Python: 201 packages went into its `site-packages`, an editable
   `tradie` pointing at the run's deleted folder among them. Bash on a local worker runs as the owner, with
   nothing in the way. Slice 2 now covers it.
2. **Nothing ran the tests for the review.** The worker's test step knows npm, pnpm and yarn only, so the tests
   check was empty, and Theo approved on Maya's word: "I checked the code by reading it and did not re-run
   pytest myself". Slice 2 now covers it.
3. **The write outside the directory was not a check.** Theo saw it in Maya's handover and approved, rightly
   for the diff. Once slice 2's sandbox refuses the write, there is nothing left to approve past.

What held: Peter planning on a model, assignment by role, a real Claude Code run with a shell, a teammate's
hunk-level review with a comment, Done from an approved review, and a `file://` repository from clone to Done.

## Decided

### The autonomy switch

- One switch per company, off by default. Only the company's owner turns it on. From M8 the instance's Owner and
  Admins can remove the option for the whole instance.
- With it on, no person reviews, merges or approves a live write. A reviewer teammate's approval closes a
  review, the board merges an approved pull request whose tests are green, and live writes run under the
  company owner's standing approval. Peter hires, adds departments and fires at once.
- Sign-off rules still bring a person in for what they name (Rules, below). Needs-you keeps those, failures,
  budget alerts, and whatever a git host refuses.
- What stays: every live write is still proposed, bound to the sha256 of its exact payload, executed only when
  the hash matches, and recorded. Its approval is recorded as decided by the company owner who turned autonomy
  on, citing the rule that allowed it, so every actor is still a person or a teammate. Teammates never mark
  Done; an approved review does. A person can veto any review, and after a merge the veto opens a revert pull
  request.
- New, because nobody is watching: Pause and Resume per company (running runs stop at their next heartbeat,
  nothing new is claimed, Peter stops planning), and budgets that stop a run mid-way.

### Rules

- Two kinds, kept apart in the UI. Enforced rules are checked by the board, and an agent cannot argue past
  them: tool modes (today's off, read and ask), web domains, repositories and branches, paths a teammate may
  not touch, spend, hiring limits, firing thresholds, and sign-off rules that bring a person back for named
  changes. Guidance is plain text every teammate gets in its instructions: coding standards, tone, security
  practice. A model follows guidance, nothing guarantees it, and the UI says so.
- Enforced rules are set in forms, never as free text, so a model never writes security policy.
- A rule that brings a person back is a sign-off rule: in Core concepts an Approval is already a proposed
  external write, so the name stays apart from it.
- Company, department and project levels, each only narrowing the one above, as policy does today; M8 adds the
  instance above every company. A rule can name teammates by tag.
- "Big changes need a person" is a starter set of sign-off rules a company's owner turns on in one click: a
  change that touches CI, deploy, migration, dependency or auth paths; a change over 400 lines; a new
  connection.

### Peter staffs the company

- Company first. A goal's work goes to the teammates the company has, matched by tags and load, and Peter hires
  only for what it lacks.
- A function the company does not have gets a department. A goal that needs marketing, in a company without
  it, makes Peter add Marketing with its lead and hire into it, because the company needs marketing from then
  on. A new department's policy starts as the company's rules and can only tighten.
- Hires belong to the company and stay after the goal. Each hire is an event in Activity, with Peter as the
  actor.
- Each hire gets a unique name, a role, tags, a persona, an engine and a model the company allows, and tools
  inside the company's ceiling. Every team has a teammate tagged `reviewer` who did not author the work.
- With no model, Peter does not hire: people hire by hand, as today.
- With autonomy off, the hires and a new department come as one draft a person accepts, as the architect's
  proposals do today, and each firing is a proposal a person accepts.

### Firing

- Peter fires a teammate who goes unused or misses the company's thresholds. Each threshold is an enforced rule
  with a default. Results: more than half of the last 10 reviews sent back or vetoed. Cost: a cost per approved
  task over 3 times the median of the teammates with the same tags. Use: no work for 30 days.
- A firing names its reason, with the numbers, in Activity.
- A fired teammate is archived: their history stays, and their name is never reused in the company. Their open
  tasks go back to Peter to reassign, and their tokens are revoked. A company's owner or admin can restore them
  within 30 days. If the work is still needed, Peter hires a replacement set up differently: another model, or a
  persona rewritten from the review comments.
- Peter never fires himself or a department lead; only a person can.
- Drift (M6) stays a signal, never a gate: it compares a teammate with their own history. Firing uses the
  company's thresholds.

### Limits

- 30 teammates and 10 departments per company by default, as enforced rules. No cap per goal: hiring is for the
  company. At the limit Peter fires before he hires, and only a teammate who already meets a firing reason; when
  nobody does, the hire waits in Needs-you. The goal caps (tasks, depth, tokens) stay.

### Names and tags

- Peter gives his hires human first names, unique in the company and never reused there, and keeps his own. The
  built-in templates keep their names for hiring by hand; a second hire from one gets a new name.
- Tags are short labels Peter picks and people can edit, such as `engineer`, `frontend`, `postgres` or
  `research`. One is reserved: reviews go to teammates tagged `reviewer`, in place of matching role text. Peter
  assigns by tags and load, and rules, Costs and the team views filter by tag.

## Slices

Each slice is green on typecheck, lint, format and the offline tests (and helm lint when the chart changes),
carries its doc lines, and is committed before the next starts. An adapter replays answers recorded from the
real service, never hand-written ones.

The slices become GitHub issues, one per slice, each pointing back here (`docs/agents/issue-tracker.md`). Each
slice is one pull request from its own worktree off `main`, built with Matt Pocock's engineering skills:
`improve-codebase-architecture` on the area first, `codebase-design` for its interfaces, `tdd` for the change,
and `code-review` before the pull request, whose body follows `pr`.

Until slice 12 ships the switch, every company runs as it does with autonomy off: slices 9 and 10 build Peter's
hires and firings as drafts and proposals, and slice 11's merge step runs only for a company with the switch on,
so nothing merges without a person before slice 12.

## The rules it changes

In the slice that ships them, each of these changes, in every place it is written:

- The human gates (slice 12). "Autonomy by default. Human gates only for merges and live external writes"
  gains "unless a company's owner turns on full autonomy; then the company's enforced rules are its gates". The
  same gate is written in `CLAUDE.md`'s opening paragraph and its rules; in `docs/plan.html`'s "What we are
  building" (`#what`), its rules (`#rules`), the Tool mode row of Core concepts ("No mode lets a live write skip
  the gate") and its borrowed ideas ("a live write always asks"); and in `docs/security.md`'s first guarantee
  ("A merge happens on your git host by your hand; a write to a live system happens only through an approval").
- A decision reopened. M5 dropped the `auto` tool mode because "It contradicts 'human gates only for merges and
  live external writes'" (`docs/m5.md`, Not in M5). The switch reopens that decision, at the owner's word on
  2026-11-02, as a company setting rather than a tool mode.
- Peter's drafts (slices 9 and 12). The plan's `#peter` says "The architect's proposals (departments,
  teammates, toolboxes, policies) are always drafts a human accepts. Peter never grants a tool to anyone by
  himself." With the switch on, his hires take effect at once, with tools inside the company's ceiling.
- "Policy only narrows" covers the rules of slice 6, and in M8 the instance above every company.

Everything else in "Rules that never soften" stands: payloads bound by their hash, teammates never marking
Done, the veto, secrets, and one event stream.

## What only the owner can do

- The proof run's GitHub token, which the owner sets; no agent handles it.
- Merging every pull request of this milestone. The switch is for the companies on a board, not for this
  repository.

## Demo script

On real models, from the docs:

1. A company with only Peter, on Claude Code, autonomy on and the starter rules turned on.
2. A goal against a throwaway repository. Peter picks the team and hires it, each teammate with a name and tags,
   a reviewer among them.
3. He assigns the work by tags; the team builds, the reviewer approves, and the board merges.
4. A task that touches a migration waits in Needs-you.
5. A goal that needs marketing makes Peter add Marketing and hire into it; a later goal reuses that hire.
6. With the results threshold set low, a teammate whose work keeps coming back is fired and replaced, and
   Activity names the reason and the numbers.
7. Pause mid-run stops the run; a budget set below what is left stops the next run part way.
